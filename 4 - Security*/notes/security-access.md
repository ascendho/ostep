# security-access

## 核心结论
访问控制是操作系统安全的核心机制，核心目标是**“决定主体（用户/进程）能否以特定方式（读/写/执行）访问客体（文件/设备等资源）”**。其通过“引用监控器”执行决策，核心依赖两种基础机制：访问控制列表（ACL）和能力机制（Capabilities）——ACL以“客体为中心”记录授权主体，能力机制以“主体为中心”持有访问凭证。现代系统多结合二者优势（如Linux先用ACL验证，后用能力机制优化访问效率），并通过自主/强制访问控制、基于角色的访问控制（RBAC）等扩展，平衡安全性、易用性和管理效率，最终落地安全策略。

## 一、核心问题（CRUX）
1. 操作系统如何基于安全策略，判断某个主体对某个客体的访问请求是否合法？
2. 如何设计访问控制机制，兼顾决策准确性、执行效率和管理灵活性？
3. 如何解决“授权管理”问题（如批量授权、权限撤销、角色变更）？
4. 如何在分布式、多用户场景下，确保访问控制的一致性和安全性？

## 二、关键概念与核心原则
### 2.1 三大核心要素
- **主体（Subject）**：发起访问请求的实体，如用户、进程；
- **客体（Object）**：被访问的资源，如文件、设备、IPC通道；
- **访问模式（Access Mode）**：访问的具体方式，如读（r）、写（w）、执行（x）、创建、删除等。

### 2.2 核心原则
- **完全中介（Complete Mediation）**：每次访问都需经过访问控制决策，不可省略（避免“一次授权永久生效”的漏洞）；
- **最小权限（Least Privilege）**：仅授予主体完成任务必需的最小权限，减少权限滥用风险；
- **权限分离（Separation of Privilege）**：关键操作需多重权限叠加，避免单一权限泄露导致系统妥协。

### 2.3 决策核心：引用监控器（Reference Monitor）
- 定义：执行访问控制决策的核心模块，需满足“正确实现、高效执行、不可绕过”三大要求；
- 工作流程：接收主体的访问请求→查询安全策略（如ACL、能力列表）→返回“允许”或“拒绝”结果。

## 三、两种基础访问控制机制
访问控制的核心是“如何编码安全策略”，主流分为ACL和能力机制，二者设计思路完全相反，各有优劣：

### 3.1 访问控制列表（ACL：Access Control List）
#### 核心逻辑：以“客体为中心”，记录“谁能访问该客体”
- 本质：为每个客体（如文件）维护一份授权列表，记录主体及对应的访问权限；
- 决策流程：主体请求访问客体→系统查询该客体的ACL→判断主体是否在列表中，且权限匹配→允许/拒绝访问。

#### 经典实现：Unix九位ACL（至今仍被广泛使用）
- 设计背景：早期Unix受存储限制，用9个比特位编码权限，平衡简洁性和实用性；
- 结构：
  1. 所有者（Owner）：3位（读r、写w、执行x）；
  2. 组（Group）：3位（同组用户的权限）；
  3. 其他用户（Others）：3位（非所有者、非同组用户的权限）；
- 优势：存储开销小，与inode紧密结合，查询高效（无需遍历长列表）；
- 局限：仅支持三类主体，无法表达复杂授权关系（如特定用户组的细粒度权限）。

#### 优缺点
| 优势                                  | 劣势                                  |
|---------------------------------------|---------------------------------------|
| 易查询“某客体的授权主体”（直接看ACL）  | 难查询“某主体的所有授权客体”（需遍历所有ACL） |
| 权限撤销简单（修改客体ACL即可）        | 分布式场景下需统一用户身份命名空间（如跨机器用户ID一致性） |
| 与文件系统元数据（如inode）结合紧密，性能好 | 长列表查询开销高（需优化存储结构）    |

### 3.2 能力机制（Capabilities）
#### 核心逻辑：以“主体为中心”，持有“访问客体的凭证”
- 本质：主体（进程）持有一组“能力凭证”，每个凭证对应“某客体+特定访问模式”，凭证是访问的唯一依据（类似“钥匙”）；
- 决策流程：主体请求访问客体→提交对应的能力凭证→系统验证凭证有效性（是否合法、未撤销）→允许/拒绝访问。

#### 关键要求：不可伪造与可控传播
- 不可伪造：能力凭证需受OS保护（如存储在 kernel 内存，用户进程无法篡改），避免主体伪造凭证；
- 可控传播：主体无法直接复制/传递凭证，需通过OS系统调用申请传递（如进程A请求OS将“文件X的读权限”传递给进程B），OS可基于策略拒绝。

#### 优缺点
| 优势                                  | 劣势                                  |
|---------------------------------------|---------------------------------------|
| 易查询“某主体的所有授权客体”（直接看能力列表） | 难查询“某客体的所有授权主体”（需遍历所有主体的能力列表） |
| 权限传递灵活（主体可选择性传递部分能力） | 凭证存储与管理开销高（需维护每个主体的能力列表） |
| 适合细粒度权限控制（如仅允许访问文件某部分） | 权限撤销复杂（需回收所有相关凭证，若凭证已复制则难以彻底撤销） |
| 分布式场景下无需统一身份命名空间（凭证本身包含客体标识） | 需解决凭证伪造问题（依赖OS或加密技术） |

### 3.3 实际系统的混合使用
现代OS多结合二者优势，避免单一机制的缺陷：
- 示例（Linux文件访问）：
  1. 首次访问（open()）：查询文件ACL，验证主体权限；
  2. 后续访问（read()/write()）：OS为进程创建“能力类结构”（如文件描述符关联的权限记录），直接查询该结构，无需重复访问ACL；
  3. 关闭文件（close()）：销毁该“能力类结构”，下次访问需重新验证ACL。

## 四、访问控制的两种授权模式
根据“谁能决定权限”，访问控制分为自主和强制两类，可叠加使用：

### 4.1 自主访问控制（DAC：Discretionary Access Control）
- 核心：客体所有者可自主决定谁能访问该客体，及访问模式（如用户可将自己的文件授权给好友）；
- 特点：灵活易用，符合日常使用习惯；
- 局限：无法防止“授权主体泄露权限”（如用户授权好友后，好友将文件转发给第三方）；
- 适用场景：普通桌面、服务器（如Linux、Windows默认模式）。

### 4.2 强制访问控制（MAC：Mandatory Access Control）
- 核心：权限由系统管理员（或安全策略）强制指定，客体所有者无法修改（如军事系统的“绝密”文件，普通用户无法授权给低权限用户）；
- 特点：安全性高，适合严格保密场景；
- 局限：灵活性差，管理成本高；
- 示例：NSA开发的Linux变体（如SELinux）、军事系统的分级保密机制。

## 五、扩展：基于角色的访问控制（RBAC）
### 5.1 核心思想：按“角色”授权，而非直接给“用户”授权
- 解决问题：批量授权与权限管理（如公司“程序员”角色统一授予代码库访问权限，新员工入职仅需分配角色）；
- 核心要素：
  1. 角色（Role）：一组权限的集合（如“销售员”=“读客户数据”+“写订单”）；
  2. 用户（User）：可分配多个角色（如员工可同时是“销售员”和“团队管理员”）；
  3. 权限（Permission）：“客体+访问模式”的组合。

### 5.2 关键特性
- 最小权限：角色仅包含完成任务必需的权限；
- 角色切换：用户可临时切换角色（如经理切换为“程序员”测试代码，切换后仅拥有程序员权限）；
- 职责分离：关键操作需多个角色协作（如“审批订单”和“执行付款”分属不同角色）。

### 5.3 实际系统实现
- Linux/Unix：通过“组+setuid/sudo”模拟简易RBAC：
  - 组：对应基础角色（如“wheel”组用户可执行sudo）；
  - setuid：程序运行时临时获取所有者权限（如`passwd`命令以root权限运行，普通用户可修改自己的密码）；
  - sudo：授权用户临时以其他角色（如root）执行命令，需二次认证；
- 高级RBAC：如企业级系统的专用RBAC模块（支持角色分级、权限继承）。

## 六、实际场景中的访问控制
### 6.1 Android的权限模型
- 核心：每个App对应独立用户ID（UID），基于“权限标签（Permission Label）”控制访问；
- 流程：
  1. App开发时声明所需权限（如“读取联系人”“使用相机”）；
  2. 用户安装时需同意权限请求（或后续在系统设置中修改）；
  3. App运行时，OS验证其权限标签是否匹配访问请求；
- 特点：属于强制访问控制，App无法自主获取未声明的权限，符合移动设备“单用户多App”的安全需求。

### 6.2 权限提升的风险与控制
- 风险：攻击者通过漏洞获取低权限后，可能通过“权限提升”（如利用setuid程序漏洞）获取root权限，完全控制系统；
- 控制措施：
  1. 严格限制setuid程序的数量和功能（仅保留必要程序，如`passwd`）；
  2. setuid程序需严格校验输入，避免缓冲区溢出等漏洞；
  3. sudo配置精细化（仅授权必要用户执行必要命令）。

## 七、总结
1. 访问控制的核心是“基于策略的二元决策”，依赖ACL和能力机制两种基础模型，现代系统多混合使用以平衡性能和灵活性；
2. 自主访问控制适合普通场景，强制访问控制适合高保密场景，RBAC解决大规模权限管理问题；
3. 实际实现需兼顾“完全中介”（确保每次访问都校验）和“效率”（如缓存权限凭证减少重复查询）；
4. 安全风险多源于“策略设计不当”（如过度授权）而非机制缺陷，需结合最小权限、角色分离等原则优化策略。
