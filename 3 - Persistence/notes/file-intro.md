# file-intro

## 核心结论
文件系统的核心是将原始磁盘块抽象为**文件（字节数组）** 和**目录（文件名→inode映射）**，通过统一的UNIX API提供持久化存储访问。其关键设计是“inode（存储文件元数据）+ 目录树（组织文件）+ 文件描述符（进程级访问句柄）”，支撑起随机访问、共享、权限控制、原子更新等核心能力。使用时需关注API细节（如`fsync()`需同步目录、`lseek()`不触发磁盘寻道）和机制差异（硬链接vs符号链接），避免一致性或权限问题。

## 一、核心问题（CRUX）
OS如何管理持久化设备，将原始磁盘块转化为用户友好的文件和目录？如何通过API支持文件的创建、读写、共享、权限控制和原子更新，同时保证数据持久化和一致性？

## 二、核心抽象
### 2.1 文件（File）
- 本质：**线性字节数组**，OS不感知文件结构（如文本、图片），仅负责持久化存储和准确读取；
- 标识：低级别名称为**inode号（i-number）**，是文件的唯一标识，存储在inode数据结构中；
- 核心特性：可创建、读写、删除，支持顺序/随机访问，通过元数据记录大小、权限、所有者、访问时间等信息。

### 2.2 目录（Directory）
- 本质：**（用户可读名称 → inode号）的映射表**，每个条目指向文件或其他目录；
- 特殊条目：
  - `.`（dot）：指向目录自身；
  - `..`（dot-dot）：指向父目录；
- 目录树：从根目录（UNIX中为`/`）开始，通过路径分隔符（`/`）组织所有文件和目录，形成层级结构（如`/foo/bar.txt`）。

## 三、文件系统核心API与机制
### 3.1 文件操作：创建、读写与关闭
#### 1. 创建文件
- 核心调用：`open(path, flags, mode)`，通过`O_CREAT`标志创建文件；
- 关键参数：
  - `O_WRONLY`：仅写模式；
  - `O_TRUNC`：文件已存在则截断为0字节；
  - `mode`：权限位（如`S_IRUSR|S_IWUSR`表示所有者可读可写）；
- 兼容调用：`creat(path, mode)`，等价于`open(path, O_CREAT|O_WRONLY|O_TRUNC, mode)`，现已较少使用。

#### 2. 读写文件
- 核心流程：`open()`获取文件描述符 → `read()`/`write()`读写 → `close()`关闭；
- 文件描述符（File Descriptor）：
  - 进程私有整数，映射到系统级“打开文件表”条目；
  - 默认占用3个描述符：0（标准输入）、1（标准输出）、2（标准错误）；
- 示例（`cat`命令的系统调用流程）：
  ```
  open("foo", O_RDONLY) → 返回3 → read(3, buffer, 4096) → write(1, buffer, 6) → close(3)
  ```

#### 3. 随机访问：lseek()
- 功能：修改文件的“当前偏移量”，支持随机读写，**不触发磁盘寻道**（仅修改OS内存中的偏移变量）；
- 关键参数（`whence`）：
  - `SEEK_SET`：偏移量设为`offset`字节；
  - `SEEK_CUR`：偏移量设为当前值+`offset`；
  - `SEEK_END`：偏移量设为文件大小+`offset`；
- 示例：`lseek(fd, 200, SEEK_SET)` → 下一次读写从文件第200字节开始。

### 3.2 共享文件访问：打开文件表
#### 核心机制
- 打开文件表（Open File Table）：系统级结构，存储文件的当前偏移量、读写权限、inode指针、参考计数（`ref`）；
- 进程文件描述符数组：每个条目指向打开文件表的一个条目；
- 共享场景：
  1. `fork()`：子进程继承父进程的文件描述符，共享同一打开文件表条目，参考计数+1；
  2. `dup()`/`dup2()`：创建新文件描述符，指向同一打开文件表条目，参考计数+1；
- 关键：参考计数为0时，OS释放该打开文件表条目。

### 3.3 数据持久化与一致性
#### 1. 强制持久化：fsync()
- 问题：`write()`仅将数据写入OS缓存，并非立即写入磁盘，断电可能丢失；
- 功能：强制将文件的“脏数据”（未写入磁盘的缓存数据）写入磁盘，返回即保证数据持久化；
- 注意：创建新文件时，需同时`fsync()`文件所在目录，确保目录条目（文件名→inode）也持久化。

#### 2. 原子重命名：rename()
- 特性：**原子操作**（系统崩溃时，文件要么是旧名，要么是新名，无中间状态）；
- 典型用途：原子文件更新（如编辑器保存）：
  1. 写入新内容到临时文件（`foo.txt.tmp`）；
  2. `fsync()`临时文件；
  3. `rename("foo.txt.tmp", "foo.txt")` → 原子替换旧文件。

### 3.4 文件元数据与删除
#### 1. 元数据（Metadata）
- 存储：文件的元数据（大小、inode号、权限、所有者、访问/修改/状态变更时间）存储在`inode`中；
- 访问调用：`stat(path)`（通过路径）或`fstat(fd)`（通过文件描述符），填充`stat`结构体。

#### 2. 删除文件：unlink()
- 原理：删除目录中“文件名→inode”的映射，**减少inode的链接计数**；
- 关键：仅当链接计数为0时，OS才释放文件的inode和数据块（真正删除）；
- 命令关联：`rm`命令本质是调用`unlink()`。

### 3.5 目录操作
#### 1. 创建与删除

- 创建：`mkdir(path, mode)` → 创建空目录（含`.`和`..`条目）；
- 删除：`rmdir(path)` → 仅能删除空目录（仅含`.`和`..`）。

#### 2. 读取目录
- 核心调用：`opendir(path)` → `readdir(dp)`（循环读取目录条目） → `closedir(dp)`；
- 目录条目结构（`struct dirent`）：包含文件名（`d_name`）和对应的inode号（`d_ino`）；
- 示例：`ls`命令本质是通过`opendir()`+`readdir()`读取目录，结合`stat()`获取元数据。

## 四、链接机制：硬链接与符号链接
### 4.1 硬链接（Hard Link）
#### 实现
通过`link(oldpath, newpath)`创建，本质是在目录中添加新的“文件名→inode”映射，与原文件指向**同一inode**。

#### 关键特性

- 无额外存储开销，仅增加目录条目和inode的链接计数；
- 限制：不能跨文件系统（inode号仅在单个文件系统内唯一）、不能链接目录（避免目录树循环）；
- 优势：删除原文件后，硬链接仍可访问（链接计数>0），无悬空引用。

### 4.2 符号链接（Symbolic Link/Soft Link）
#### 实现
通过`ln -s oldpath newpath`创建，本质是**独立文件**（文件类型为`l`），存储的是原文件的路径（而非inode号）。

#### 关键特性
- 有额外存储开销（存储路径字符串），与原文件是不同inode；
- 无限制：可跨文件系统、可链接目录；
- 劣势：原文件删除后，符号链接指向无效路径（悬空引用）。

### 4.3 核心对比表
| 特性                | 硬链接                          | 符号链接                          |
|---------------------|---------------------------------|-----------------------------------|
| 实现方式            | 目录条目指向同一inode           | 独立文件存储原文件路径            |
| 链接计数            | 增加inode的链接计数             | 不影响原文件链接计数              |
| 跨文件系统          | 不支持                          | 支持                              |
| 链接目录            | 不支持                          | 支持                              |
| 悬空引用            | 不会出现                        | 原文件删除后出现                  |
| 存储开销            | 无（仅目录条目）                | 有（存储路径字符串）              |

## 五、权限控制
### 5.1 UNIX权限位
- 格式：如`-rw-r--r--`，共9位，分为三组（所有者、组、其他用户）；
- 权限含义：
  - 读（r）：文件可读取，目录可列出条目；
  - 写（w）：文件可修改，目录可添加/删除条目；
  - 执行（x）：文件可运行，目录可`cd`进入；
- 修改：`chmod`命令（如`chmod 600 foo.txt` → 所有者读写，其他无权限）。

### 5.2 高级权限：访问控制列表（ACL）
- 作用：弥补权限位的局限性，支持对特定用户/组设置精细化权限（如仅允许用户A读取目录）；
- 示例：AFS文件系统的`fs setacl`命令，可指定用户的“ lookup/insert/delete/read/write”等权限。

## 六、文件系统挂载（Mount）
### 6.1 核心流程
1. 创建文件系统：`mkfs -t type device`（如`mkfs -t ext3 /dev/sda1`），在磁盘分区上创建空文件系统（含根目录）；
2. 挂载：`mount -t type device mountpoint`（如`mount /dev/sda1 /home/users`），将新文件系统“粘贴”到目录树的挂载点；
3. 统一访问：多个文件系统（如ext3、tmpfs、AFS）通过挂载融入同一目录树，访问路径统一（如`/home/users/a/foo`）。

### 6.2 关键特性
- 挂载点原目录内容被隐藏，卸载后恢复；
- 系统启动时，`/etc/fstab`配置自动挂载的文件系统。

## 七、关键提示与坑点
1. **lseek()不触发磁盘寻道**：仅修改OS内存中的文件偏移量，磁盘寻道仅在实际读写时发生；
2. **rename()的原子性**：是实现文件原子更新的核心，避免更新过程中系统崩溃导致的数据不一致；
3. **fsync()需同步目录**：创建新文件时，需同时`fsync()`文件和所在目录，确保文件名→inode映射也持久化；
4. **TOCTTOU问题**：检查（如`stat()`验证文件类型）与操作（如`write()`）之间存在时间窗口，可能被恶意用户篡改文件（如替换为符号链接），需谨慎处理高权限程序；
5. **目录的执行位**：无执行位则无法`cd`进入目录，即使有读权限也无法列出条目。

## 八、核心总结
1. 抽象核心：文件（字节数组）和目录（文件名→inode映射）简化了持久化存储的使用，目录树提供统一的命名空间；
2. API设计：注重统一和灵活性，`open()`/`read()`/`write()`等基础API支撑所有文件操作，特殊API（`fsync()`/`rename()`）解决一致性和原子性需求；
3. 关键机制：inode存储元数据、文件描述符管理进程级访问、链接机制支持文件共享、挂载统一多文件系统，共同支撑起共享、权限、一致性等核心需求；
4. 使用要点：需关注API细节（如`fsync()`的正确使用）和机制差异（硬链接vs符号链接），避免因误解导致数据丢失或权限问题。
