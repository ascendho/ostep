# dist-afs

## 核心结论
AFS（Andrew File System）是为解决“大规模分布式文件共享”设计的客户端/服务器文件系统，核心创新是**“全文件缓存+回调机制”**——通过客户端本地磁盘缓存完整文件，结合服务器主动通知的回调机制，大幅减少客户端与服务器的交互，提升可扩展性（单服务器支持客户端数量从20增至50）；同时提供简单易懂的缓存一致性语义（close-to-open+同机即时可见），并引入文件标识符（FID）、全局命名空间等特性，弥补了NFS在可扩展性、一致性和易用性上的不足。其核心是从NFS的“无状态、块级缓存”转向“有状态、文件级缓存”，以少量状态维护为代价，换取更高的可扩展性和更清晰的用户体验。

## 一、核心问题（CRUX）
1. 如何设计分布式文件系统，让单服务器支持更多客户端，解决NFS中“频繁服务器校验”导致的可扩展性瓶颈？
2. 如何提供简单易懂的缓存一致性语义，避免NFS因依赖缓存超时导致的行为模糊？
3. 如何减少客户端与服务器的交互开销，同时保证跨客户端文件访问的合理性？
4. 如何在提升可扩展性的同时，兼顾安全性、全局命名空间等实用特性？

## 二、AFS版本演进：从v1到v2
AFS的核心改进源于对v1的实测优化（遵循“先测量再构建”的原则），v1的设计缺陷推动了v2的关键创新。

### 2.1 AFSv1：基础设计与问题
#### 核心设计
- **全文件缓存**：客户端打开文件时，将整个文件下载到本地磁盘缓存，后续读写操作完全本地执行，关闭文件时若修改则同步至服务器；
- **协议操作**：通过`Fetch`（获取文件）、`Store`（存储文件）、`TestAuth`（校验文件是否变更）等协议，客户端需主动校验缓存有效性。

#### 关键问题（导致可扩展性瓶颈）
1. **路径遍历开销高**：`Fetch`/`Store`请求需传递完整路径名，服务器需反复遍历目录树查找文件，消耗大量CPU；
2. **校验请求泛滥**：客户端频繁发送`TestAuth`请求确认缓存有效性，服务器大部分时间用于回应“文件未变更”，资源浪费；
3. **负载不均与进程开销**：服务器未支持负载均衡，且为每个客户端创建独立进程，上下文切换开销大。

### 2.2 AFSv2：核心改进（解决可扩展性问题）
针对v1的缺陷，AFSv2引入两大核心改进，同时保留全文件缓存的基础设计：
1. **回调机制（Callback）**：服务器与客户端建立“状态约定”——服务器承诺“文件变更时主动通知客户端”，客户端无需主动发送`TestAuth`校验，默认缓存有效；
2. **文件标识符（FID）**：替代完整路径名，由“卷标识+文件标识+唯一标识符”组成，客户端自行遍历路径并缓存中间目录的FID，服务器无需重复路径遍历；
3. **其他优化**：引入“卷”实现负载均衡（管理员可迁移卷至不同服务器），服务器用线程替代进程减少上下文切换开销。

## 三、核心设计：可扩展性与一致性的平衡
### 3.1 全文件缓存（客户端本地磁盘）
- **缓存单位**：以“整个文件”为单位缓存到客户端本地磁盘（而非NFS的“块级内存缓存”）；
- **读写流程**：
  1. 首次打开文件：客户端通过FID逐步查找目录→下载完整文件到本地缓存→建立回调；
  2. 读写操作：直接操作本地缓存文件，无网络交互；
  3. 关闭文件：若文件修改，将完整文件同步至服务器，服务器触发其他客户端的回调失效。
- **优势**：减少网络交互频率，尤其适合“重复访问同一文件”的场景（二次访问完全本地）；
- **劣势**：大文件部分读写效率低（需下载/上传整个文件）。

### 3.2 回调机制（Callback）：减少服务器交互的核心
#### 核心逻辑
- 客户端获取文件时，服务器与之建立“回调”（本质是服务器的状态记录：“该客户端缓存了某文件”）；
- 当文件被其他客户端修改并同步至服务器时，服务器主动向所有缓存该文件的客户端发送“回调失效”通知；
- 客户端收到通知后，标记缓存文件为“无效”，下次访问需重新从服务器获取。

#### 核心价值
- 替代NFS的“主动轮询校验”，将“客户端拉取”改为“服务器推送”，大幅减少服务器请求压力，提升可扩展性。

### 3.3 文件标识符（FID）：避免服务器路径遍历
- **组成**：卷标识（指定文件所属卷）+ 文件标识（卷内唯一）+ 唯一标识符（避免ID重用冲突）；
- **作用**：客户端首次访问文件时，自行遍历路径（如`/home/remzi/notes.txt`），缓存每个目录的FID，后续访问直接使用FID，服务器无需重复路径遍历，节省CPU资源。

### 3.4 缓存一致性模型：简单易懂的语义
AFS的一致性模型比NFS更清晰，分为两种场景：
1. **不同客户端（跨机器）**：遵循“close-to-open”语义——客户端修改文件后，仅当`close()`时同步至服务器，服务器同时触发其他客户端的回调失效；其他客户端下次`open()`时需重新获取最新文件，确保不会读取 stale 数据；
2. **同一客户端（同机器）**：写操作即时可见——本地多个进程访问同一文件时，无需等待`close()`，直接读取最新缓存内容，符合UNIX本地文件语义；
3. **冲突处理**：跨客户端并发修改时，“最后关闭者获胜”（last closer wins）——最终服务器存储的是最后一个`close()`的完整文件，避免NFS的“块混合”问题。

## 四、崩溃恢复：有状态设计的代价
AFSv2为提升可扩展性引入“服务器状态”（回调记录），导致崩溃恢复比NFS更复杂：
### 4.1 客户端崩溃恢复
- 客户端重启后，之前的回调状态失效，无法接收服务器的“回调失效”通知；
- 恢复逻辑：客户端将所有缓存文件标记为“可疑”，下次访问时需发送`TestAuth`请求校验有效性，有效则继续使用，无效则重新获取。

### 4.2 服务器崩溃恢复
- 服务器重启后，内存中的回调记录丢失，无法知晓哪些客户端缓存了哪些文件；
- 恢复逻辑：服务器重启后向所有客户端发送“缓存失效”通知，客户端收到后标记所有缓存为“可疑”，后续访问需重新校验或获取文件。

## 五、AFS与NFS的核心性能对比
| 场景                          | AFS表现                          | NFS表现                          | 关键差异原因                          |
|-------------------------------|-----------------------------------|-----------------------------------|---------------------------------------|
| 小/中文件重复读取             | 快（本地磁盘/内存缓存，无网络）   | 快（内存缓存）                    | 缓存单位不同（文件vs块），二次访问均无网络交互 |
| 大文件重复读取                | 快（本地磁盘缓存）                | 慢（需重新从服务器获取）          | NFS仅内存缓存，大文件超出内存需重传    |
| 大文件部分读写                | 慢（需下载/上传整个文件）         | 快（仅传输目标块）                | AFS全文件缓存，NFS块级缓存            |
| 跨客户端文件更新可见性        | 清晰（close后立即失效回调）       | 模糊（依赖缓存超时）              | AFS回调推送，NFS主动轮询校验          |
| 服务器可扩展性                | 高（减少校验请求和路径遍历）      | 低（频繁GETATTR和路径遍历）       | AFS回调+FID设计减少服务器负载          |

## 六、AFS的其他关键特性
1. **全局命名空间**：所有客户端看到统一的文件路径（如`/home/remzi/notes.txt`），无需手动挂载协调，易用性优于NFS；
2. **安全性与访问控制**：支持用户认证和细粒度访问控制列表（ACL），可灵活控制文件访问权限，安全性远超早期NFS；
3. **负载均衡**：通过“卷”（Volume）机制，管理员可将卷迁移至不同服务器，平衡负载；
4. **管理友好**：提供完善的服务器管理工具，简化大规模部署后的运维。

## 七、总结
1. AFS的核心创新是“全文件缓存+回调机制”，通过减少客户端-服务器交互，解决了NFS的可扩展性瓶颈；
2. 一致性模型设计简洁易懂，兼顾“跨客户端合理性”和“同客户端易用性”，避免NFS的模糊行为；
3. 与NFS形成互补：AFS适合“重复访问、完整读写”的场景，NFS适合“部分读写、大文件随机访问”的场景；
4. 遗产影响：虽市场份额被NFS（开源标准）和CIFS挤压，但回调、全局命名空间、ACL等设计被NFSv4借鉴，影响深远。
